# CLAUDE.md

Guidance for working in this repo. It's the race-simulation engine — no UI, no build step of its own beyond `tsc` for typechecking and `tsx` for running its CLI tools. See `README.md` for the architecture (condition parsing, sample policies, `RaceSolver.ts`'s numerical integration).

## What this repo is

`mackoz/uma-skill-tools`, a fork of [`alpha123/uma-skill-tools`](https://github.com/alpha123/uma-skill-tools), used as a **git submodule** by [`mackoz/uma-tools`](https://github.com/mackoz/uma-tools) (the browser app built on top of this engine) — the same relationship `alpha123/uma-tools` has with its own engine submodule. Most of what's imported beyond the alpha123 baseline came from [`Werseter/uma-skill-tools@kachi`](https://github.com/Werseter/uma-skill-tools/tree/kachi).

## The submodule workflow — read this before editing

**Changes here don't reach `mackoz/uma-tools` automatically.** The flow is: edit here → commit → push to `origin` (this repo) → in `mackoz/uma-tools`, `cd uma-skill-tools && git pull` (or checkout the new commit) → commit the resulting gitlink bump in `mackoz/uma-tools`. If you're working from a session that has both repos checked out as siblings, don't edit the copy inside `mackoz/uma-tools/uma-skill-tools/` expecting it to persist — that's a submodule checkout, not this repo's working tree; edits there are just as real but need the same commit-here-then-bump-there flow, and it's easy to lose track of which checkout you're actually in.

## Branching & PRs

- **Prefer one open PR in this repo at a time — soft guidance, not a hard rule.** Before creating a branch, check for an existing open PR/branch covering the same area (`gh pr list`) and push to that branch instead of branching off the default branch again, when the new work is genuinely the same thread. If it isn't (a second, unrelated PR is really warranted), that's fine — just flag it and confirm with the user before opening it, rather than opening a second PR silently.
- A PR merged here isn't done until `mackoz/uma-tools` bumps its submodule gitlink (see the workflow above).
- **This repo has a pre-commit hook** (`.githooks/pre-commit`, PIPE-67): it refuses a commit whose staged *added* lines look like a macOS/Linux home path (`/Users/<user>/...`, `/home/<user>/...`), a sanitized Claude transcript directory name (`-Users-<user>-github-...`), or a pattern from an untracked per-user file at `${XDG_CONFIG_HOME:-$HOME/.config}/uma-tools/pii-patterns` (one POSIX-ERE pattern per line — literals, `\.`, `[...]`, `|`, `.*`; no `\d`/`\b`/`\w`, which awk doesn't know and the JS hook in uma-tools would read differently; `#` comments allowed) — that's where a real name or email address belongs, never in a tracked file. One-time setup per clone: `git config core.hooksPath .githooks`. A genuine false positive can be committed with `--no-verify`.

## Hard rules

1. **Never hand-edit `data/*.json`.** These are Perl-generated from the game's `master.mdb` (`tools/make_skill_data.pl` → `data/jp/skill_data.json`, `tools/make_skillnames.pl` → `data/jp/skillnames.json`, `tools/make_course_data.pl` → `data/jp/course_data.json`). Edit the generating `.pl` script and regenerate. The one exception this repo's history has needed: a small number of specific, individually-verified value corrections sourced from a real `master.mdb` query or an already-computed-and-verified value from alpha123's data, applied via a short one-off script (not by hand) when a full regen wasn't possible — see the `Fix HP-1` commit for the pattern, and don't treat it as a precedent for casual hand-edits. `data/global/skill_data.json`, `data/global/skillnames.json`, and `data/global/course_data.json` are the Global counterparts, generated by the same `.pl` scripts run against a different (Global) `master.mdb`. `data/global/tracknames.json` is the odd one out, same as `data/jp/tracknames.json`: there's no `make_tracknames.pl` (no generator exists), so both are hand-maintained, not Perl-generated — don't apply this rule's "regenerate, don't hand-edit" instruction to either. All four `data/global/` files are inert storage as far as this engine is concerned, regardless of how each is produced: `RaceSolverBuilder.ts`/`CourseData.ts` always resolve `data/jp/`, never `data/global/`. The only consumer is `mackoz/uma-tools`'s web app, for its Global build. See `mackoz/uma-tools`'s `CLAUDE.md` JP/Global data-split table for the fuller cross-reference.
2. **Engine-only, no DOM/UI dependencies.** This code runs inside a web worker (`mackoz/uma-tools`'s `simulator.worker.ts`) and under plain `tsx` for the CLI tools in `tools/` — don't import Preact, browser globals, or anything that assumes a DOM.
3. **`Random.ts`'s `Rule30CARng` is not what its name says.** It's an alias for a `prando`-backed PRNG, not a real Rule-30 cellular-automaton generator — don't assume alpha123's semantics or numeric output apply just because the class name matches something alpha123's engine also has.
4. **Pacer skill triggers are sampled once per race slot, not once per scenario** (`prepPacerTriggers`, called before the scenario loop — `mackoz/uma-tools`'s `umalator/compare.ts` is the one caller; `buildPacer` only indexes the precomputed table). The operational trap: this was a genuine numeric-output change, so if you're diffing simulator output against a pre-`0861c8f` run and a virtual pacemaker is involved, expect a difference — that's the fix, not a regression. Full rationale and rejected alternatives: `docs/adr/0007-pacer-triggers-once-per-slot.md`.
5. **Significant design decisions get an ADR.** `docs/adr/` records the *why* behind modeling approximations, numeric-output-affecting designs, and failure-handling posture — including reconstructed rationale for inherited decisions. Before "fixing" something surprising (the RNG shim, the field-condition stand-ins, the loud unknown-condition errors), read the matching record; when a change settles a question that could have gone another way, add or amend one (see `docs/adr/README.md` for the format).
6. **`// ANCHOR: <name>` comments are cited from `uma-tools-plans` docs (PIPE-8, widened PIPE-3).** The sibling private repo cites this engine's code by marker (`RaceSolver.ts@spot-struggle-duration`) instead of by line number, so a citation survives an unrelated commit moving the line — but only if the marker itself stays put. Don't delete or rename an `ANCHOR` comment without checking whether a doc cites it (`uma-tools-plans/scripts/check-citations.py` catches this if you have that repo checked out as a sibling); a marker can move with its code freely, it just can't disappear or be renamed silently. Adding a new one is free — one comment line above the site it names, kebab-case, at least one hyphen, unique across this repo and `mackoz/uma-tools`. A marker is for one specific line/expression that *is* the claim being cited; a doc citing a whole function, field, or table instead names it as a bare symbol (`RaceSolver.ts` / `applyLaneMovement()`) with no marker at all — don't feel obligated to add an `ANCHOR` just because a doc happens to cite this file.

## Known gaps (see `README.md`'s Caveats for the full list)

- Skill cooldowns are implemented, scaled by course distance (`Cooldown = BaseCooldown * CourseDistance[m] / 1000`, see `plans/game-mechanics/skills.md:49-54`), but only some condition families actually re-trigger after re-arming: `all_corner_random` and the distribution/erlang family (`near_lane_time`, `change_order_onetime`, `blocked_*`) draw multiple candidate points and can re-trigger, while `straight_random` and `is_finalcorner_random` resolve to a single candidate point for the race and never do (`plans/condition-reference/conditions.md`). `accumulatetime` alone resolves to `ImmediatePolicy` (0 spares) and cannot re-trigger on its own, but ANDed with one of the distribution conditions above it reconciles to that condition's policy and does re-arm. The direct position-pinning path used by `tools/replay/replayDiff.ts` bypasses condition-based triggering entirely and can double-fire — see `README.md`'s "Skill cooldowns" section.
- No skill-level scaling table (levels 1–10, up to 1.25x) — tracked separately as SKL-9. Value and
  duration scaling are now partially modeled, in `ValueScaling.ts`: `ability_value_usage` 2
  (`MultiplySkillNum`), 8/9 ("Multiply Random", unchanged, stochastic — handled separately in
  `RaceSolver.ts`'s `scaleEffectValue()`), 13 (`MultiplyMaximumRawStatus`), and 22/23
  (`MultiplySpeed`); `ability_time_usage` 3 and 7 (`MultiplyRemainHp`). Every other code — 62 JP
  skills carry a non-Direct code on some effect, ~40 of them still uncovered by the above — falls
  through to exactly `1.0`, via one table in `ValueScaling.ts` that states the reason per group
  (scenario/account state this simulator can't model, field/blocking/lead state sampled
  statistically rather than modeled, missing skill-tag data, or undocumented). See
  `docs/adr/0013-value-scaling-identity-fallthrough.md` for the rationale and `README.md`'s
  "Scaling effects" section for the reference list.
- `accumulatetime` combined with a distribution-modeled condition may still activate earlier than the distribution predicts (no per-skill exemption list, unlike alpha123's engine).
- A handful of shipped skill conditions (`temptation_opponent_count_behind`/`_infront`, `is_other_character_activate_advantage_skill`, plus 15 JP-only names) aren't registered in `ActivationConditions.ts`'s `Conditions` table — 18 unregistered names total. Referencing one now throws a named `ConditionParser` `ParseError: unknown condition: <name>` at skill-build time instead of a bare `TypeError` — see `README.md`'s "Unknown skill conditions now fail loudly, by name" section. `test/arb/Race.ts`'s `isUnregisteredConditionError()` lets the property-based harness (`test/race.ts`) recognize this specific, intentional error and treat the generated case as vacuous rather than a failure — it can still turn up for a skill the module-load-time `skillids` filter didn't catch, since that filter can't exhaustively probe every course/order-info combination a precondition might key off, only every strategy. `temptation_opponent_count_behind`/`_infront` in particular never reaches this error via `RaceSolverBuilder.addOpponentDebuff` (HP-7): the victim-safe path (`victimSafeCondition()`, `docs/adr/0014-victim-safe-debuff-conditions.md`) strips any `temptation_opponent_count_*` clause — it's not on the allowlist — before the condition is parsed, so an incoming debuff using it never hits the unregistered-condition check at all. Adding a skill with that condition any other way (`addSkill`) still throws as documented above.

## `test/`, `tools/`, and pre-existing `tsc` errors

As of 2026-09-05 (PIPE-53), the engine's compiler is `typescript@7.0.2` with `@types/node@24` (previously `typescript@4.7.4`/`@types/node@18`; both bumped together — `@types/node@22+`'s `typesVersions` targets TS 5.x+, so bumping either alone against the other's old partner produced an unbuildable intermediate). `npx tsc --noEmit` (also runnable as `npm run typecheck`, added by PIPE-52) still reports the same **7 pre-existing errors**, all in `tools/gain.ts`/`tools/dump.ts` (CLI tools calling an older `RaceSolver` constructor shape) — **the compiler bump introduced zero new errors.** Two of the seven did change code under TS 7: the two `pacer`-object-literal errors that were `TS2345` under 4.7.4 are now `TS2561` ("Object literal may only specify known properties... Did you mean to write 'isPacer'?"), a friendlier message for the same underlying mismatch. These predate this documentation update and aren't part of the bundled engine surface (`mackoz/uma-tools`'s builds only pull in the top-level `.ts` files, not `test/`/`tools/`). Don't treat a clean browser build as proof these pass, and don't feel obligated to fix them incidentally while touching something else — they're a separate cleanup task. (Previously 12, five of which were in `test/` — PIPE-46 fixed the `HorseDesc.mood` drift those five traced back to. Before that, 14: `RaceSolverBuilder.ts`'s two errors — a dangling `EnhancedHpPolicy` import and a `HorseDesc` missing the `skills` field `setupPacer()` reads — were fixed by HP-5/PIPE-22.)

**`tsconfig.json` pins `"strict": false`, deliberately.** TypeScript 4.7 defaulted `strict` off; TypeScript 7.0.2 defaults it **on**. Neither this engine's nor the parent's `tsconfig.json` ever set the key explicitly, so the PIPE-53 compiler bump would have silently turned on `strictNullChecks`/`noImplicitAny`/`strictPropertyInitialization` — measured at **284 errors** (vs. 7 with strict off) under the toolchain this ticket actually installs — 277 net-new findings on top of the 7-error baseline, spread across `tools/` (163), `test/` (52) and the engine core (69). Pinning `strict: false` keeps this ticket a pure compiler sync with an unchanged error baseline; adopting strict is real, valuable work but touches numerically-sensitive engine core where guards/assertions risk perturbing simulation output, so it belongs in its own reviewed ticket (PIPE-59) rather than folded into a toolchain bump. This also means `mackoz/uma-tools`'s own "implicit-any dominated" ~1000-diagnostic-cap backlog is largely the same strict-mode default nobody opted into — that repo's `tsconfig.json` has no `strict` key either — worth knowing before reading its count as a deliberate baseline, though out of scope here.

**TypeScript 7 ships no `tsserver`.** The Go rewrite's npm package declares only `{"tsc"}` as a
binary — `node_modules/typescript/lib/` contains `tsc.js` and a path shim, with no `tsserver.js`.
Nothing automated depends on it (the compiler, the tests and the builds all still work; esbuild
never used the TypeScript API at all), but an editor configured to use the *workspace* TypeScript
rather than its own bundled copy loses language features — completions, go-to-definition, hover
types, as-you-type diagnostics — and does so **silently**, since a language client that can't find
`tsserver.js` typically degrades rather than erroring. VS Code's bundled extension is unaffected;
third-party LSP clients that hardcode the `node_modules/typescript/lib/tsserver.js` path (several
neovim setups, Sublime's LSP-typescript) are the ones that notice. If your editor's TypeScript
support goes quiet in this repo, this is why. Note `mackoz/uma-tools` has been in exactly this
state since it adopted 7.0.2, ahead of this engine — PIPE-53 only brought the two into line.

**`npm test` no longer typechecks as a side effect.** PIPE-52 moved every harness invocation from `ts-node` (which typechecks by default) to `tsx` (which does not — it's a pure esbuild transform, indifferent to which `typescript` version is installed, which is exactly what unblocks PIPE-53's compiler bump). `npm run typecheck` is the standalone replacement for that coverage; it is deliberately not chained into `npm test` because the 7 pre-existing `tools/` errors above would make that chain permanently red.

## Running tests

`npm run lint:tests` (PIPE-76) is this engine's only linter — a `biome.json` scoped to
`files.includes: ["test/**"]`, formatter and assist disabled (this is a fork of
`alpha123/uma-skill-tools`; bulk-formatting it would create permanent diff noise against upstream
for no gain), with `linter.rules.suspicious.noFocusedTests`/`noSkippedTests`/
`noDuplicateTestHooks`/`noExportsInTest` at `"error"`. It runs `biome lint --only=<rule>` for
each of the four rather than a bare `biome check .`, since this engine has no general lint
config or format baseline to be green against. `npm test` **prepends** it, ahead of `vitest run`
— a planted `test.only`/`it.only` makes `vitest run` itself exit green (only the focused test
runs), so appending the check would sit behind the ~30s `-n 500` `race.ts` harness before
complaining; the lint check itself takes milliseconds. `test/VitestProp.ts`'s `prop()` wrapper
deliberately exposes no `.only`/`.skip` of its own for the same reason noted in its own comment:
Biome's tripwire can't see through a custom wrapper's methods, so adding either would make a
focused or skipped property test invisible to lint.

As of 2026-09-05 (PIPE-50), `npm test` runs `vitest run` first, covering nine files under `test/*.test.ts`: `test/parser.test.ts` (a `fast-check` property test round-tripping the condition parser's AST through stringify/parse — its generated trees are filtered by a `reconciledPolicy()` helper that drops any tree whose operands' sample policies can't reconcile, since both `AndOperator` and `OrOperator` reconcile at construction and the `StraightRandomPolicy`/`AllCornerRandomPolicy` pair deliberately throws; the property is syntactic, so those trees are skipped rather than generated. Roughly 0.1% of trees are excluded, and the filter's `catch` is narrowed to that one intentional message so a real double-dispatch break still fails loudly — same reasoning as `test/race.ts`'s vacuous-case handling below. Without it the test failed about one run in eight once `fast-check` reached 3.23.2), `test/activation-sampling.test.ts` (6 `test()` blocks covering `ErlangRandomPolicy`/`LogNormalRandomPolicy` sampling bounds, `deriveSeed` stream isolation, and — since SKL-29 — `DistributionRandomPolicy.sample()`'s region walk at its boundary offsets), `test/rushed-escape-roll.test.ts` (pins the fixed Rushed escape-roll behavior — exactly 3 rolls at 3s/6s/9s at 55% each, forced end at 12s, timestep-independent — against a minimal stand-in that exercises `updateRushedState()`/`endRushedState()` directly), `test/spot-struggle-duration.test.ts` (pins the DYN-8 fix: Spot Struggle duration scaled by `StrategyProficiencyModifier`, checked against replay-derived bounds for three named aptitude ranks), `test/spot-struggle-group.test.ts` (pins the DYN-14 fix: Spot Struggle's entry/exit geometry — frontmost-uma reference, lateral checks, the once-per-race-per-style gate, the absolute `EndSection` cap, and the distance/lateral exit cascade — against the game's `CompeteTop` parameter block, 13 `test()` blocks), `test/activate-counts-as-random.test.ts` (pins the UI-34 fix for `is_activate_any_skill` under `conditionsWithActivateCountsAsRandom`), `test/value-scaling-roll.test.ts` (pins the HP-6 "Multiply Random" value-scaling roll — distribution, determinism, and draw-order independence), `test/course-helpers.test.ts` (a `fast-check` property test of `CourseHelpers.isSortedByStart()`, adopted by PIPE-50 after sitting as an orphan `test/helpers.ts` that `npm test` never ran), and — added by SKL-7 — `test/value-scaling-deterministic.test.ts` (pins every implemented `ValueScaling.ts` bracket boundary against `game-mechanics/skills.md`, plus the identity return for each code the engine deliberately doesn't model). All nine currently pass, 48 `test()`/`prop()` blocks total. `test/parser.ts` used to be a stub even though `tape`/`fast-check` were already installed; `test/activation-sampling.ts` was added alongside the statistical-sampling stabilization fix; `test/rushed-escape-roll.ts` was added alongside the DYN-11 fix; `test/spot-struggle-duration.ts` and `test/spot-struggle-group.ts` were added alongside DYN-8/DYN-14. All three mechanics-pinning tests (Rushed, spot-struggle duration, spot-struggle group) share a minimal-stub pattern — a stand-in object carrying only the instance fields the method(s) under test touch, exercised via `RaceSolver.prototype.<method>.call(stub)`, rather than constructing a full `RaceSolver` — factored out into `test/RaceSolverTestHelpers.ts` (`attachMethods` for stubs whose method calls a sibling method on `this`, `field` for wiring multiple stubs into a shared `this.umas` the way `initUmas()` does, `stepUntilInactive` for the step-the-timer-then-call-until-inactive loop, `seededSubStream` for deriving per-sample RNG seeds the way production code seeds sub-streams). Reach for these first before writing a new mechanics test's stub scaffolding from scratch.

PIPE-50 migrated the first eight of these files off `tape` onto Vitest 5 (`vitest.config.mts`, `test.include: ['test/**/*.test.ts']`) — see `docs/adr/0012-vitest-unit-tests.md` for the rationale and rejected alternatives. `test/TestHelpers.ts`'s `forAll()` (a thin `fc.property`/`fc.assert` wrapper) stayed framework-free and unchanged, since `test/race.ts` — a standalone CLI harness kept on plain `tsx`, never run through the vitest runner — also imports it; the vitest-dependent `prop()` wrapper that used to live alongside it moved to a new `test/VitestProp.ts` instead, because `vitest` cannot be `require()`'d from a CommonJS module (which is how `tsx` transpiles this package's import graph, absent a `"type": "module"` in `package.json`) — `test/race.ts` now carries its own tiny local `prop()` that reports to the console and sets `process.exitCode` on failure, preserving the pre-migration behavior of failing the `npm test` `&&`-chain on a real property failure.

`npm test` also runs `test/race.ts -n 500` (three property tests over a full data-driven `RaceSolver` built through `RaceSolverBuilder` — race progression is monotonic, position is always defined, and two forked builders given the same skills stay in sync) and `test/regression/check.ts --fast` (replays a random 100-case sample of the checkpoint in `test/regression/checkpoints/` against the current build). Both were revived by PIPE-46 after rotting fully broken: `test/arb/Race.ts`'s `HorseDesc()` generator had drifted from `mood`'s move onto `HorseDesc` (`RaceSolverBuilder.ts`'s `buildBaseStats()` reads `horseDesc.mood`, not a race-level value) — the arb still generates `mood` at the race-parameter level as it always has (at the time, to preserve the arb's fast-check generation stream) and assigns it onto the generated horse via a post-generation `.map()`. That stream-preservation rationale is now moot: the 2026-09-09 lockfile refresh moved `fast-check` 3.0.1 → 3.23.2 and `pure-rand` 5 → 6, which changes the generated stream wholesale regardless. The `.map()` shape is fine to keep, but don't preserve it *for that reason*. `test/race.ts`'s default `--runs` is still 10000 (about 8 minutes and liable to turn up further engine gaps — see the Known-gaps bullet above); `npm test` uses `-n 500` (~30s) to stay fast and reliable. `test/race.ts`'s three properties wrap their whole body, but since SKL-29 they swallow *only* the unregistered-condition class (`arb.isUnregisteredConditionError`) as a vacuous case — every other exception from building or stepping a generated race is rethrown and fails the property (see its own top-of-file comment). The invariants they check are still asserted only via an explicit boolean return, never by expecting construction to succeed; what changed is that an unexpected throw out of the engine is now a finding rather than a silent skip. The previous blanket swallow is what kept SKL-29 itself invisible to this tier. `test/bench/bench.ts` (a micro-benchmark harness over the same checkpoint format, skipping any checkpoint case whose builder errored at record time), `test/regression/create-checkpoint.ts`/`knowncases.ts` (full checkpoint recording and a handful of hand-picked pinned cases) and `test/regression/replay-case.ts` (replays one recorded case and reports how many of its samples moved, for bisecting a single failure without another full recording run) remain standalone, invoked directly via `tsx`, not part of `npm test` — `create-checkpoint.ts`'s default 10000 cases takes several minutes. The current checkpoint is `20260909.5ecc3aa.2432198835.json`, re-recorded by SKL-7's second fix round (10000 cases, seed 2432198835, 18 `err` cases) — it supersedes SKL-7's own first `20260909.a9c5582.3802546203.json`, which superseded SKL-29's `20260905.bdb99bc.42.json`; each is deleted in the commit that replaces it (only one checkpoint file is kept at a time — and note `getLatestCheckpoint()` picks the newest by the filename's *date* alone, so two checkpoints recorded on the same day cannot be told apart and must not both be left in place). Both SKL-7 re-records were required, not incidental. The first: SKL-7 genuinely changed simulation output for 19 skills (see `docs/adr/0013-value-scaling-identity-fallthrough.md`), and `check.ts --fast` against the pre-SKL-7 checkpoint failed 185 of 8397 sampled assertions across 5 distinct cases — every one of those 5 involved at least one of the 19. The second: fixing value usage 13 to bracket on the maximum *raw* stat rather than the maximum adjusted stat changed output again, and a **full** `check.ts` run (933,954 assertions) against the first checkpoint failed 174 assertions across exactly 3 distinct cases, every one of which carried `210081` or `210082` — the only two skills in the JP data with value usage 13 — as either a skill under test or a presupposed skill. Both times the confinement check came *before* re-recording, which is what makes a re-record safe rather than a bug-hiding shortcut; run the full `check.ts` (not `--fast`) for it, and read `params.presupposedSkills` as well as `params.skillsUnderTest` — a first pass at the second analysis looked only at the latter and appeared to turn up an unrelated failing case that wasn't one. Note that PIPE-46 had itself fully re-recorded the checkpoints on 2026-09-04: the prior ones (2023–2025-dated, last touched by the `9c0652a` kachi import) predated this fork's entire divergence from alpha123 and could never legitimately match post-fork numeric output — see `docs/adr/` for this fork's numeric-output-affecting decisions since. Their replacement's legitimacy rests on a canary check (temporarily adding an extra `RaceSolver` constructor RNG draw made `check.ts` fail; removing it made a fixed-seed run reproducible run-to-run), not on matching the deleted recordings.

## Documentation changes

- Ticket/doc prose uses `$UMA_CODE_REPO`/`$UMA_ENGINE_REPO`/`$UMA_PLANS_REPO` or a `~`-relative form, never an absolute home path or the account holder's name — the pre-commit hook refuses it.
- When rewriting a doc (`README.md`, `docs/adr/`), keep its existing format — tables stay tables; don't convert a table to prose unless explicitly asked.
- Verify factual claims (mechanics numbers, table/column names, error behavior) against the source or a real `master.mdb` query before writing them, and cite the file you checked.

## Exploring `master.mdb`

Every generator script in `tools/` (`make_skill_data.pl`, `make_skillnames.pl`, `make_course_data.pl`) reads specific tables out of the game's `master.mdb` — see `mackoz/uma-tools`'s `docs/data-pipeline.md` for the full table list. `sqlite3` (Apple's bundled CLI, already on any Mac — `sqlite3 master.mdb` then `.tables`/`.schema <table>`/plain SQL) is the fastest way to check whether a table has the row or column a script expects before writing a one-off Perl or Node script to do the same query. No decryption needed for `master.mdb` itself — the chacha20/XOR encryption `docs/data-pipeline.md`'s "This fork's asset extraction is broken" section describes is specific to the separate `meta` asset-manifest DB (icon/asset extraction), not the skill/course/uma data these `.pl` scripts read.
